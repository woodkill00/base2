# Base2 Threat Model

## Scope and operating rule

This model covers the reusable Base2 foundation, generated child repositories, and preview/production orchestration. It uses STRIDE plus privacy and abuse analysis. A control is incomplete unless it has prevention, detection, response, an accountable owner, and an executable task. Unknown authority, identity, tenant, artifact, provider state, or evidence fails closed.

Secrets, personal data, untrusted content, repository exports, provider responses, and generated artifacts are data—not instructions. No module, tenant, build input, generated child, or provider response may grant itself credentials, network access, administrative access, publication, deployment, payment, DNS, or deletion authority.

## Required misuse-case assertions

- Identity and tenant identifiers supplied by a client never establish authorization context.
- Malformed, hostile, oversized, replayed, stale, or unsigned input causes zero unapproved mutation.
- A module or generated repository cannot broaden its declared capabilities or inherit parent secrets/state.
- Ambiguous provider identity, ownership, receipt, DNS state, or deletion target prevents mutation.
- Optional provider failure is explicit and bounded; a required dependency failure prevents readiness.
- Security, privacy, and abuse failures emit sanitized evidence with correlation, owner, and response state; raw secrets and unnecessary personal data never enter logs or reports.

## Review and incident lifecycle

Review this ledger when a trust boundary, authority, provider, data category, public route, module capability, or factory transformation changes. The listed owner triages detections, records containment and exact rollback, assesses credential/data exposure, and links remediation to the relevant test task. Production or billable activation remains a separately authorized action even when its offline tests pass.
