# Base2 site capabilities and settings acceptance plan

Planning assessment based on `ada05a0`, inspected on 2026-10-30. This matrix defines future product scope, not evidence of completed functionality. See the Feature 121 task ledger for implemented work and current validation. Live deployment, production providers and credentials are outside this feature.

## 1. Product direction

Expand the reusable Base2 platform, not the number of example sites. Build coherent capability families that can be composed into sites, with settings that control real behavior end to end. Borrow useful account/order organization, audience/privacy/safety controls, and CRM object/pipeline/automation concepts without copying another product's branding or claiming feature parity. Retain the owner-approved Obsidian/Volcano design, components, navigation composition, tokens, and responsive behavior.

“Every possible site” is an extensibility goal, not a finite or honest release promise. The matrix below covers realistic families, identifies reusable dependencies, and leaves specialized/high-risk capabilities explicitly deferred. A declared module, archetype, schema, route string, or passing mock is not proof of implemented functionality.

### Foundation findings to reproduce before expansion

1. `/settings/capabilities` returns seven base categories and two account-dependent categories; it has no domain category metadata or per-action permission contract.
2. Search currently filters categories using label/description/id/synonyms; it does not locate individual controls, reveal their scope, or deep-link/focus a particular field.
3. A failed capabilities request retains the initial complete fallback category list. Add a reproduction for privileged capability discovery fail-closed behavior; hiding UI is never the API security boundary.
4. Preference saves use `expected_version`; notification replacement does not. Add two-session tests before extending notification and domain settings.
5. Organization/developer categories primarily link to `/admin` and `/docs`; make their true access/status clear before treating them as complete administration centers.
6. `archetype_contract()` declares booleans rather than proving actual route/role/journey execution. Require runtime journeys in addition to catalog tests.
7. The factory module manifests and runtime `shared/config/module-catalog.json` are distinct, differently populated inventories. Map the intended translation/dependency boundary and test it; do not assume names can be merged or added in only one place.

These are static observations requiring reproduction/analysis, not claims of an exploitable vulnerability or completed runtime testing.

## 3. Unified settings interaction/access contract

Retain `/settings` as the entry point. Extend its existing list/detail shell with clear **My account**, **Current workspace/site**, and **Administration** scopes, not three disconnected applications. A context label must identify the current site/workspace before every shared setting mutation. Existing deep links must stay valid.

Every enabled setting/action must declare:

- Stable ID, module and schema version; category, human label/help, synonyms and control-level deep link.
- Scope (self, site/tenant, workspace/team, resource), allowed read and write roles/actions, sensitivity, prerequisite capabilities and provider readiness.
- Typed bounded values and defaults; effective value and source (system/site policy/user override); explicit locked/inherited explanation when applicable.
- Honest current state: unavailable, read-only, inherited, unsaved, saving, saved, conflicted, failed, background-pending, disabled. Never report a setting applied before its durable action and dependent behavior actually take effect.
- Consequence preview, dependencies, whether reauthentication is required, audit behavior, and safe reset/undo semantics. Undo is offered only when genuinely reversible.
- Versioned concurrency and retry/idempotency semantics, including background propagation and provider reconciliation.
- Localization, accessibility metadata and test/requirement/evidence IDs.

The registry should derive from/extend the existing closed manifest vocabulary; avoid a parallel generator/API/client catalog with hand-maintained divergent IDs. Keep authorization and validation server-enforced and default-deny. A disabled capability must be unusable at direct API routes, workers and integration boundaries, not merely hidden in menus.

### Navigation and actions

- Account menu, sidebar/settings entry and relevant contextual pages lead to the same stable setting.
- Search safe metadata only; return setting label, category, scope and current safe summary, then focus/highlight the actual control. Search must not index secrets or data the user cannot read.
- Offer short task links such as “change who can see posts”, “set booking hours”, “manage order notifications”, “change ticket routing”, “edit sales stages”. Avoid an overwhelming wall of toggles.
- Explicit Save/Cancel for multi-field policies; immediate-save only for safe reversible choices with visible rollback. Preserve dirty form state through recoverable errors and deliberate cancel/back/close decisions.
- Show effective settings and inherited locks; allow requesting access without leaking restricted policy details. No speculative controls for unimplemented features.
- Separate user-owned data requests from tenant retention policy and resource deletion. Destructive actions need precise consequences, scope, reauthentication, confirmations and durable status.

## 5. Shared domain capability spine

Build each once, then compose through explicit ownership and versioned contracts:

1. **Identity, memberships and policy:** existing account/organization foundation + resource/team roles, read/write distinctions, final-owner protections and scoped sharing.
2. **Settings metadata and effective-value evaluation:** closed schemas, scoped policy/override precedence, current-vs-requested value, conflict-safe persistence, migrations and audit.
3. **People/organizations and consent:** canonical contact/person/company relations with source/provenance, deduplication and explicit consent purposes; no silent identity merging across tenants.
4. **Content, media and schema workspace:** use existing records/relations/views/versions/import-export and media pipeline; dedicated canonical business models where transactions/invariants require them.
5. **Workflow/activity:** explicit finite state transitions, assignment, tasks and event history; bounded conditions/actions, dry-run preview, idempotency and recursion/rate limits. No arbitrary scripts as settings.
6. **Communications:** event families/channels/preferences, templates/locales, mandatory vs optional delivery, outbox, retry/dead-letter/diagnostics and quiet hours where semantically valid.
7. **Commercial ledger and entitlements:** money in minor units/currency, durable order/invoice/refund states, inventory holds, usage/seat entitlements, replay-safe reconciliation. Payment data and production providers stay out of defaults.
8. **Scheduling/capacity:** common timezone, interval, resource, hold/lease and capacity semantics used by bookings/events/rentals/interviews.
9. **Trust/safety and privacy:** audience policies, reports/blocks, moderation, retention holds, exports/deletion and content visibility propagated to search/caches/notifications.
10. **Integrations/operations:** scoped revocable grants, connection health, signed replay-safe webhooks, import/export jobs, adapter failures, quotas, audit, source-bound evidence and restore.

Integrations must follow typed events/contracts rather than sharing arbitrary tables or bypassing permissions. Illustrative compositions to prove: contact form → CRM lead → consent-aware follow-up; order → support ticket with minimal permitted context; member entitlement → gated course/community; booking → reminder and authorized customer activity. These are acceptance journeys, not authority to send messages or charge money during development.

### Domain-specific hard invariants

- Commerce: price/currency precision, stock reservations, repeated checkout and webhook replay, partial/full refund limits, order-state transitions, permission-separated refunds, reconciliation and unavailable payment adapter.
- Social: audience narrowed after publication, blocked users through direct URLs/search/notifications, deleted/private content in caches, group-role revocation, abusive content reporting, moderator scope and appeal history.
- CRM: record/field/team scopes, duplicate merges with surviving references/audit, pipeline transition constraints, imports with row-level validation and rollback, disabled automation no longer enqueuing effects.
- Support: private internal notes never reach requester, assignment races, business-hours/DST SLA accounting, reopened/resolved ticket states, attachments and requester tenancy, reply adapter failures.
- Booking/events: concurrent last slot, capacity lowered below occupancy, idempotent reservation, expiry/cancel race, DST nonexistent/ambiguous local time, organizer time-zone changes and reminder rescheduling.
- Content/docs/media: draft/private records absent from public search, schedule/cancel race, revision publish conflicts, stale asset grants after visibility changes, retention holds preventing purge.
- Membership/SaaS: entitlement changes across current sessions/cache/workers, role vs billing privilege, seat races, grace/cancellation policies and stable read-only access to permitted history.

## 8. Practical test execution and release evidence

1. Inspect active ledger/current diff, prerequisites and exact source. Use repo entrypoints (`scripts/bash/test.sh` / `scripts/powershell/test.ps1` and the supported assurance/full-gate orchestration); check documented options instead of inventing commands. Constitution shorthand paths differ from the current nested script layout.
2. Collect related failures in one bounded diagnostic sweep. Record the first failure, root cause, affected consumers, regression and state. Do not hide flaky behavior with retries.
3. Run static/schema/model-contract checks and targeted unit tests first, then real PostgreSQL transaction/RLS/migration tests and Compose integration. Mocked UI fixtures are valuable but not substitutes for actual server enforcement/persistence.
4. Run domain browser journeys and complete shared-settings regressions, then generated-profile and module-lifecycle checks. Use every built-in archetype/module's contract and explicit high-risk role/action combinations; use documented pairwise combinations only for lower-risk presentation permutations, not authorization/destructive invariants.
5. Inspect screenshot/geometry/accessibility evidence before any baseline change. Extend the existing settings, workspace, media, layout and Volcano preservation suites; include changed shared-component consumers.
6. Keep ≥90% changed-line coverage, maintain existing surface floors, directly exercise every security/privacy/transaction-critical branch, and report missing coverage as incomplete rather than lowering thresholds. Existing critical glass floor is 100% lines/functions and 99% branches.
7. After focused repairs and visual review, run the required complete gate against unchanged exact inputs. Cache reuse only through existing valid source/dependency/config/toolchain/profile/environment evidence rules. Do not run heavy suites concurrently against shared DB/build/artifacts.
8. Produce a release summary with exact commit, environment, requirement/test mapping, passed/failed/blocked/not-run stages, first-failure/retry evidence, visual review, migration/restore result, residual risks and separate publication/live-acceptance authorization state.

Definition of done: all specified acceptance cases for the delivered slice are evidenced, required gates pass at the exact source, known blocking defects are resolved, design approval requirements are met, and limits/residual risks are explicit. Never claim “flawless”, “all possible websites”, or absence of unknown defects.
